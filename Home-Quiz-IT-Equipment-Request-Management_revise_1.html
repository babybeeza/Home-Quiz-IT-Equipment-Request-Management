IT Equipment Request Management System

ระบบจัดการคำขอใช้อุปกรณ์ IT


พัฒนา Web Application สำหรับให้พนักงานส่งคำขอใช้อุปกรณ์ IT เช่น Notebook, Monitor และอุปกรณ์เสริม พร้อม workflow ให้ผู้ดูแลตรวจสอบ อนุมัติ หรือปฏิเสธคำขอ

RECOMMENDED TIME

8–12 ชั่วโมง

APPLICATION ROLES

Employee · Approver

FRONTEND

Next.js · React · TypeScript

BACKEND

Spring Boot · Kotlin · Maven

ไม่จำเป็นต้องทำระบบ Authentication จริง สามารถจำลอง Role จากหน้าเว็บหรือ Request Header ได้

Business Rules

  1. Employee แก้ไขคำขอได้เฉพาะสถานะ DRAFT
  2. ก่อน Submit คำขอต้องมีรายการอุปกรณ์อย่างน้อย 1 รายการ
  3. จำนวนอุปกรณ์แต่ละรายการต้องอยู่ระหว่าง 1–5 ชิ้น
  4. ต้องระบุวันที่ต้องการใช้งาน และวันที่ต้องไม่เป็นอดีต
  5. การปฏิเสธคำขอต้องระบุเหตุผล
  6. Backend ต้องตรวจสอบ Business Rule และสถานะทุกครั้ง ไม่เชื่อข้อมูลสถานะที่ Client ส่งมา
  7. ต้องปฏิเสธสถานะหรือ transition ที่ไม่ถูกต้อง พร้อมจัดการ concurrent update ด้วย Version

04 / FRONTEND

Form, List & State

ซ่อน Action ที่ใช้ไม่ได้ใน UI แต่ API ต้องตรวจสอบซ้ำ

4.1 Request Form

  • เพิ่มและลบ Equipment Item แบบ Dynamic
  • แสดง Field Validation และ Cross-field / Business Validation
  • แสดง Loading State และป้องกัน Submit ซ้ำ
  • เก็บข้อมูลเดิมเมื่อ API Error; Reset เมื่อบันทึกสำเร็จ
  • แสดง Dirty State และเตือนก่อนออกจาก Form ที่ยังไม่บันทึก
  • รองรับ Edit Mode
  • Map Server-side Validation Error ไปยัง Field ที่เกี่ยวข้อง
  • เมื่อ Version Conflict แจ้งผู้ใช้และไม่เขียนทับข้อมูลใหม่อัตโนมัติ

ตัวอย่าง Server Validation Error ที่ต้อง map ไปยัง Employee Email และ Required Date:

{

  "code": "VALIDATION_ERROR",

  "message": "Request validation failed",

  "fieldErrors": {

    "employeeEmail": "Email format is invalid",

    "requiredDate": "Required date must not be in the past"

  }

}

4.3 Search, Filter & Pagination

ค้นหาจาก Request Number, Title หรือ Employee Name; กรอง Status และ Department; ใช้ Search กับ Filter ร่วมกันได้ รองรับ Pagination, จำนวนรายการทั้งหมด, Empty State และ Sort ตาม Created Date

แนะนำให้เก็บ Search Parameters ใน URL เช่น /requests?keyword=notebook&status=PENDING&page=0&size=10

4.4 React State & Hooks

แสดงความเข้าใจ useState, useEffect, Form/API/Derived State, Immutable Update และ Custom Hook อย่างน้อย 1 ตัว ใช้ useMemo หรือ useCallback เมื่อมีเหตุผล ไม่เก็บ Derived State ซ้ำ จัดการ Dependency, Cleanup, Stale Response และ Race Condition ให้ถูกต้อง และแยก Server State จาก UI State อย่างเหมาะสม

ตัวอย่าง Custom Hook: useEquipmentRequests, useEquipmentRequestForm, useDebounce, useUnsavedChanges อนุญาตให้ใช้ React Query หรือ SWR พร้อมอธิบายเหตุผล

06 / DESIGN

Architecture & Database

แยก Responsibility ให้ชัด ไม่จำเป็นต้องใช้ Clean Architecture เต็มรูปแบบ

Backend Architecture

equipment-request-service/

└── src/main/kotlin/com/example/equipment/

    ├── controller/

    ├── application/

    ├── domain/

    ├── repository/

    ├── dto/

    ├── exception/

    └── configuration/

└── src/test/kotlin/com/example/equipment/

  • Controller ไม่เก็บ Business Logic; Service/Application Layer ควบคุม Use Case
  • ไม่ส่ง Entity เป็น API Response โดยตรง; แยก Request DTO และ Response DTO
  • กำหนด Mapping Responsibility, Transaction Boundary และ Exception Handling ให้ชัดเจน
  • ตั้งชื่อให้อ่านเข้าใจ และหลีกเลี่ยง Nullable Type โดยไม่จำเป็น

Database Design

Table

ข้อมูลสำคัญ

equipment_requests

id, request_number, employee_name, employee_email, department, title, purpose, required_date, additional_note, status, rejection_reason, version, created_at, updated_at

equipment_request_items

id, request_id, equipment_type, quantity, specification, created_at, updated_at

Database Expectations

  • ใช้ UUID เป็น Primary Key และกำหนด request_number เป็น Unique
  • มี Foreign Key จาก Item ไปยัง Request และ Index สำหรับ Field ที่ใช้ค้นหาบ่อย
  • ใช้ Optimistic Locking ผ่าน version (เช่น JPA @Version)
  • ไม่ใช้ ddl-auto=create เป็นวิธี Production Migration
  • ใช้ Flyway หรือ Liquibase เป็น Bonus หรือกำหนดเป็น Requirement สำหรับระดับ Senior

Transaction: การบันทึก Request และ Items ควรอยู่ในขอบเขต Transaction ที่เหมาะสม หากบันทึก Item ไม่สำเร็จ ต้องไม่เหลือ Request ที่ถูกบันทึกเพียงบางส่วน

07 / RELIABILITY

Concurrency, Errors & Validation

ข้อมูล Client อาจเก่า ผิดรูปแบบ หรือถูกแก้ไขได้เสมอ

Optimistic Locking / Version Conflict

  1. User A และ User B เปิดคำขอ Version 1
  2. User A แก้ไขสำเร็จ ทำให้คำขอเป็น Version 2
  3. User B ส่งข้อมูล Version 1; Backend ต้องปฏิเสธและไม่เขียนทับข้อมูล Version 2

HTTP 409 Conflict

{

  "code": "REQUEST_VERSION_CONFLICT",

  "message": "This request has been updated by another user",

  "fieldErrors": {}

}

Error Response Standard

ทุก Error ใช้รูปแบบเดียวกัน เช่น Validation Error, Version Conflict และ State Conflict

{

  "timestamp": "2026-09-25T10:30:00+07:00",

  "status": 400,

  "code": "VALIDATION_ERROR",

  "message": "Request validation failed",

  "path": "/api/v1/equipment-requests",

  "fieldErrors": {"employeeEmail": "Email format is invalid"}

}

HTTP Status

กรณีใช้งาน

400

Request format หรือ Field Validation ไม่ถูกต้อง

404

ไม่พบ Equipment Request

409

Version Conflict หรือ State Conflict

422

Business Rule ไม่ผ่าน

500

Unexpected Error

Frontend Validation

ให้ Feedback เร็ว ลด Request ที่ผิดพลาด แสดง Error ใกล้ Field และปรับปรุง User Experience

Backend Validation

ป้องกันข้อมูลไม่ถูกต้อง ตรวจ Business Rule และรองรับ Client นอกเหนือจาก Web Application

ห้ามพึ่ง Frontend Validation เพียงอย่างเดียว; Backend ต้องตรวจ Field, Business Rule, Role และ State ซ้ำทุกครั้ง

08 / TESTING

Frontend Test Cases

อย่างน้อย 4 กรณี; รายการต่อไปนี้เป็นแนวทางทดสอบพฤติกรรม

ใช้ Vitest หรือ Jest ร่วมกับ React Testing Library และเน้นผลลัพธ์ที่ผู้ใช้สังเกตได้ มากกว่ารายละเอียด Implementation

  1. แสดง Error เมื่อกรอก Required Field ไม่ครบ
  2. เพิ่มและลบ Equipment Item ได้
  3. ป้องกันการ Submit ซ้ำระหว่าง Loading
  4. แสดง Server-side Validation Error ที่ Field ที่เกี่ยวข้อง
  5. เมื่อบันทึกสำเร็จ รายการได้รับการอัปเดตและ Form ถูก Reset ตามที่กำหนด
  6. Search และ Filter ทำงานร่วมกันได้
  7. เมื่อเกิด Version Conflict แสดงข้อความเหมาะสมและไม่เขียนทับข้อมูลใหม่อัตโนมัติ

เกณฑ์สำคัญ

ทดสอบ Loading, Error, Empty และ Success State ตามความเหมาะสม โดยยืนยันพฤติกรรมจากมุมมองผู้ใช้

09 / TESTING

Backend Test Cases

อย่างน้อย 6 กรณี; ครอบคลุม Business Rule และสถานะ

ใช้ JUnit 5 ร่วมกับ MockK หรือ Mockito; เพิ่ม Integration Test ได้ตามความเหมาะสม

  1. สร้าง Draft สำเร็จและได้ข้อมูลตอบกลับถูกต้อง
  2. สร้างคำขอโดยไม่มี Item ไม่สำเร็จเมื่อ Submit
  3. Submit จาก DRAFT เปลี่ยนเป็น PENDING สำเร็จ
  4. Approve คำขอจากสถานะที่ไม่ใช่ PENDING ไม่สำเร็จ
  5. Reject โดยไม่มี Reason ไม่สำเร็จ
  6. แก้ไข Request ที่ไม่ใช่ DRAFT ไม่สำเร็จ
  7. Request ที่ไม่มีอยู่คืน 404
  8. Version ไม่ตรงกันคืน 409 และไม่เขียนทับข้อมูลล่าสุด
  9. ค้นหาด้วย Keyword และ Status ได้ผลลัพธ์ถูกต้อง
  10. Transaction Rollback เมื่อบันทึก Item ไม่สำเร็จ

แนวทาง: ตรวจทั้งผลลัพธ์, HTTP Status, Error Contract และการคงสภาพข้อมูลเมื่อคำสั่งล้มเหลว
